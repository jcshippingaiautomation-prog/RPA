# ช่องกรอกครบทุกช่อง (Field Registry) + คลัง Master ข้อมูล

## ต้องทำก่อนใช้งาน — รัน SQL 1 ครั้ง

เปิด **Supabase → SQL Editor → New query** วางไฟล์นี้แล้วกด Run:


- หน้า **คลัง Master** ขึ้นข้อความเตือนและใช้งานไม่ได้

## 1. ทะเบียนช่อง (Field Registry)

ไฟล์เดียวคุมทุกอย่าง: `rpa-import-node/src/data/field-registry.json` — **324 ช่อง**
สร้างจาก **การสำรวจหน้าจอ DCTK จริง** (ไม่ใช่การเดา) ด้วย `node dist/survey-cli.js`

| หน้า | ช่องทั้งหมด | บังคับ | RPA กรอกให้ | DCTK เติมเอง | มีคอลัมน์ DB | มีตัวเลือกให้เลือก |
|---|---|---|---|---|---|---|
| 1 · ใบขนสินค้าขาออก | 96 | 35 | 17 | 20 | 21 | 11 |
| 2 · ใบกำกับสินค้า | 82 | 37 | 8 | 4 | 8 | 12 |
| 3 · รายการสินค้า (ต่อรายการ) | 146 | 59 | 17 | 23 | 15 | 15 |

ครอบคลุมทุกอย่างที่หน้าจอ DCTK มี รวมถึงส่วนที่เครื่องมือรุ่นก่อนมองไม่เห็น:
- **ตารางราคาและค่าใช้จ่ายเต็มตาราง** (หน้า 2 และ 3 หน้าละ 68 ช่อง) — 10 แถว
  (ราคา/หน่วย · ราคา · ค่าขนส่ง · ค่าระวาง · ค่าประกัน · ค่าบรรจุ · Inland · Landing · ค่าใช้จ่ายอื่น 1-2)
  × 6 คอลัมน์ (สกุลเงิน · อัตราแลกเปลี่ยน · เงินต่างประเทศ · เงินบาท · วิธีเฉลี่ย · ปัจจัยเงื่อนไข)
- **แท็บสิทธิประโยชน์/ภาษีอากร** ของหน้า 3 — BOI · Free Zone · IEAT · คลังสินค้าทัณฑ์บน ·
  ชดเชยอากร · มาตรา 19 ทวิ · Re-Export · สูตรการผลิต · ใบอนุญาต · การรับรองถิ่นกำเนิด
- **แผงภาษีอากร/วางประกัน** ของหน้า 1 — ธนาคารค้ำประกัน · RGS · บัตรภาษี · AEO
- ช่องที่หายไปทั้งหมดเพราะไม่มี `id`: ทุกช่องเงิน/น้ำหนัก/ปริมาณ

แต่ละช่องมี:

| ฟิลด์ | ความหมาย |
|---|---|
| `key` | ชื่อช่องในฟอร์ม/`extra_fields` |
| `label` `group` `page` | การแสดงผล — หัวข้อกลุ่มตามใบขนจริง |
| `type` | text / textarea / number / combo / dropdown / date / checkbox |
| `selector` `selectorConst` | ที่อยู่ของช่องในหน้า DCTK |
| `column` | คอลัมน์จริงใน DB · `null` = เก็บใน `extra_fields` (jsonb) |
| `scope` | `header` (หัวใบ) หรือ `item` (ต่อรายการสินค้า) |
| `fill` | มี logic กรอกเฉพาะทางอยู่แล้ว |
| `computed` | **DCTK เติมให้เอง** — ฟอร์มโชว์อ่านอย่างเดียว และ RPA ห้ามกรอกทับ |
| `ai` | ให้ AI สกัดจากเอกสาร |

### วิธีสำรวจ DCTK ใหม่ (เมื่อกรมฯ เปลี่ยนหน้าจอ)


- ไม่ตั้ง = สร้างใบร่างใหม่แล้วกรอก+Save เพื่อไล่ไปหน้า 2/3 (ใช้ `SURVEY_INVOICE=Test900`)
- `SURVEY_STOP_AFTER=1` = สำรวจแค่หน้า 1 (ฟอร์มสร้างใบใหม่ ไม่แตะอะไรเลย)
- ผลลัพธ์: `file download/survey/page{1,2,3}.json` + screenshot ทุกแท็บ

### วิธีเพิ่ม/แก้ช่อง (เดิมต้องแก้ 5 ที่ ตอนนี้เหลือ 1)

1. แก้ตารางใน `scripts/gen_registry.py` (ป้ายชื่อ / ผูกคอลัมน์ DB / computed / AI) แล้วรันใหม่
2. `cd rpa-import-node && npm run build`

**ไม่ต้อง** เพิ่มคอลัมน์ใน DB · **ไม่ต้อง** แก้ `PAGE_FIELDS` ในหน้าเว็บ · **ไม่ต้อง** เขียน `put()` ใน `pages.ts`
— ช่องที่ `column = null` จะถูกเก็บใน `extra_fields` และกรอกด้วย **ตัวกรอกทั่วไป** `fillFromRegistry()` โดยอัตโนมัติ

### กติกาความปลอดภัยของตัวกรอกทั่วไป (`pages.ts` → `fillFromRegistry`)

ตัวกรอกนี้ทำงาน **ต่อท้าย** logic เดิมเสมอ และแตะเฉพาะช่องที่ปลอดภัย:

1. แตะเฉพาะช่อง `column = null` — ช่องที่มีคอลัมน์ยังใช้ logic hard-code เดิมที่พิสูจน์แล้วว่านิ่ง
2. ข้ามช่อง `computed` ทุกช่อง — **ห้ามกรอกทับค่าที่ DCTK เติมเองจากรหัสสินค้า/พิกัด**
   (เคยพลาดตรงนี้: กรอก `0` ทับค่าประกัน → Message Validate → พิมพ์ใบขนไม่ออก)
3. กรอกเฉพาะช่องที่ "มีค่าจริง" — ไม่มีค่า = ไม่แตะ
4. ช่องที่ Master ตั้งเป็น `ไม่กรอก` → ข้าม
5. กรอกช่องไหนไม่สำเร็จ → log แล้วไปต่อ ไม่ทำให้ทั้งใบล้ม

> ✅ ตอนนี้ **ทั้ง 324 ช่องอ้างอิงได้ด้วย `#id` หรือ `[name=...]`** (271 + 53) ไม่ต้องพึ่งตำแหน่ง `div` อีก
> เพราะตัวสำรวจจับคู่ input 2 ชั้นของ Kendo ได้แล้ว (ตัวที่คนพิมพ์ ไม่มีชื่อ / ตัวที่ส่งค่าจริง มีชื่อแต่ถูกซ่อน)
> เครื่องมือรุ่นก่อนกรอง "เฉพาะที่มองเห็น" ทิ้ง จึงเหลือแต่ตัวที่ไม่มีชื่อ — เป็นเหตุที่ช่องเงินทั้งหมดเคยอ้างอิงไม่ได้

## 1.5 เงื่อนไขของระบบ DCTK (ถอดมาแล้ว — ระบบเราตรวจเองได้)

ไฟล์: `rpa-import-node/src/data/field-rules.json` (สร้างโดย `scripts/gen_rules.py`)

**ถอดมา 3 ทาง เรียงตามความน่าเชื่อถือ:**

| ทาง | ได้อะไร | จำนวน |
|---|---|---|
| `Term/GetFactor` (endpoint ของกรมฯ) | ตาราง Incoterms → ช่องค่าใช้จ่ายไหนกรอกได้/ถูกปิด | 15 เงื่อนไข |
| `data-val-*` (validation จาก model ฝั่ง server) | ช่องบังคับ · ความยาวสูงสุด · ช่องที่ต้องเป็นตัวเลข | 162 ช่อง |
| ทดลองสลับค่าจริงบนหน้าจอ | "ถ้าช่อง X = ค่านี้ → ช่อง Y เปิด/ปิด/ถูกตั้งค่าให้" | 28 กฎ |
| อ่านโค้ด JS ในหน้า (792 KB) | กฎข้ามช่องที่ทำให้บันทึกไม่ผ่าน | 5 กฎ |
| ยิงทดลอง endpoint ตรวจสอบของกรมฯ | กฎฝั่งเซิร์ฟเวอร์ตอนกดบันทึก | 3 กฎ |
| ดึงรายการค่าจากคอมโบที่ค้นจากเซิร์ฟเวอร์ | รายการค่าที่กรมฯ ยอมรับ | 8 ชนิด |

### ตารางเงื่อนไข Incoterms (กฎทางการจากเซิร์ฟเวอร์กรมฯ)

DCTK แปลงราคาทุกใบไปเป็น **FOB** → ช่องค่าใช้จ่ายที่ไม่ต้องใช้ในการแปลง จะถูก **ปิด + ล้างเป็น 0**

| Incoterms | ค่าขนส่ง | ค่าระวาง | ค่าประกัน |
|---|---|---|---|
| FOB | ปิด | **ปิด** | **ปิด** |
| CFR | ปิด | กรอกได้ | **ปิด** |
| CIF · CIP | ปิด | กรอกได้ | กรอกได้ |
| EXW | กรอกได้ | **ปิด** | **ปิด** |
| CPT · FAS · FCA · DAF · DAP · DAT · DDP · DDU · DEQ · DES | กรอกได้ | กรอกได้ | กรอกได้ |

> ⚠️ ตอนดึงตารางนี้ต้องส่ง `ToTermCode=FOB` ด้วย — ถ้าส่งค่าว่าง เซิร์ฟเวอร์คืน factor คนละชุด
> (ครั้งแรกหลงตรงนี้ ได้ตารางที่กลับหัวกับความจริง)

### ระบบเราเอาไปใช้ยังไง

`validateDeclarationFull()` ตรวจก่อนกดรัน RPA และตอนเปิดใบขน:

1. **ความยาวเกิน** — เช่น "เที่ยวเรือ" ยาว 31 ตัว แต่กรมฯ รับ ≤ 12 → **ผิดพลาด** (บล็อกการรัน)
2. **ช่องที่ต้องเป็นตัวเลข** — กรอกตัวหนังสือมา → **ผิดพลาด**
3. **Incoterms ปิดช่องไหน**
   - ระดับหัวใบ → **เตือน** (DCTK แค่ล้างเป็น 0 ให้ ไม่ทำให้บันทึกไม่ผ่าน)
   - ระดับรายการสินค้า → **ผิดพลาด** (RPA จะพยายามกรอกช่องที่ปิดอยู่ → แถวนั้นล้ม)

ฟอร์มยัง **จำกัดความยาวตั้งแต่ตอนพิมพ์** (35 ช่องมี `maxlength` ตามที่กรมฯ กำหนด)

### กฎฝั่งเซิร์ฟเวอร์ที่ยิงทดลองแล้ว (`ExInvoice/CheckValidateSave`)

ยิงด้วยค่าจริงจากใบขนที่มีอยู่ แล้วเปลี่ยนทีละอย่าง 16 แบบ:

| ทดลอง | ผลจากกรมฯ |

| วันที่ใบกำกับ **หลัง** วันที่ส่งออก | ⛔ *"วันที่ใบกำกับสินค้าไม่สามารถมากกว่าวันที่ส่งออกได้"* |
| รหัสประเทศไม่มีจริง (ZZ) หรือตัวเดียว (V) | ⛔ *"รหัสประเทศผู้ซื้อ ระหว่าง ใบขน กับ ใบกำกับสินค้า ไม่ตรงกัน"* |
| เลขที่อ้างอิงไม่ตรงกับใบ | ⛔ *"Invoice No (…) ซ้ำกับหมายเลขอ้างอิง …"* |
| ช่องว่างทุกช่อง · เลขผู้เสียภาษีมั่ว · เลขใบกำกับยาว 40 ตัว | ✅ ผ่าน (กรมฯ ไม่ตรวจที่ขั้นนี้) |

> ⚠️ **บทเรียนสำคัญ: ต้องตัดคอมเมนต์ออกก่อนวิเคราะห์โค้ด**
> DCTK มีกฎที่เขียนไว้แล้ว "ปิดทิ้ง" ด้วย `//` เยอะมาก ถ้าไม่ตัดออกจะได้กฎผี 178 ข้อ
> ที่ระบบจริงไม่ได้บังคับ เช่น *"เงินต่างประเทศ ค่าระวาง ไม่สามารถเป็น 0 ได้"* และ
> *"น้ำหนักรวมหีบห่อ ต้องไม่น้อยกว่า น้ำหนักสุทธิ"* — **สองข้อนี้ถูกปิดไว้ ห้ามเอามาใช้**
> (ถ้าบังคับ จะบล็อกใบขนที่ถูกต้อง)

วิธีดึงรายการ:
```bash
COMBO_DECL_NO=DCTK000034914 COMBO_DEEP=1 COMBO_PAGES=3 node dist/combo-lists-cli.js
```
`COMBO_DEEP=1` = ไล่พิมพ์ A-Z, 0-9 แล้วรวมผล (จำเป็นเพราะกรมฯ กรองตามตัวอักษรนำ)

### ตรวจความครอบคลุมของการสำรวจ — 3 เรื่องที่ยืนยันแล้ว

**ก. ชนิดเอกสารใบขน 10 แบบ → ฟอร์มเหมือนกันหมด**

DCTK มีชนิดเอกสาร 10 แบบ (ใบขนขาออก · ผ่านแดน · ของเร่งด่วน · โอนย้ายเข้าเขตปลอดอากร ·
คำร้องขอทำลาย ฯลฯ) ทดลองเปลี่ยนทีละแบบแล้วเทียบสถานะทุกช่อง (`dist/survey-doctypes-cli.js`):

> **ทั้ง 10 แบบให้ฟอร์มเดียวกันเป๊ะ — 147 ช่อง ต่างกัน 0 จุด**
> แปลว่าที่สำรวจจากชนิด "1-ใบขนสินค้าขาออก" ใช้ได้กับทุกชนิด

**ข. ฟอร์มสร้างใหม่ vs ใบเก่า (หน้า 2) → เหมือนกันทุกประการ**

เดิมหน้า 2/3 สำรวจจากการเปิด "ใบเก่า" ซึ่งอาจถูกล็อกช่องไว้
ทดลองเปิดฟอร์มใบกำกับเปล่าด้วยปุ่ม "เพิ่มข้อมูล" (`dist/survey-fresh-cli.js`) แล้วเทียบ:

> **92 ช่องเท่ากัน · ไม่มีช่องที่โผล่เฉพาะฟอร์มใหม่ · สถานะ readonly/บังคับ ต่างกัน 0 ช่อง**

(หน้า 3 เข้าฟอร์มสร้างใหม่ไม่ได้ — ตารางส่วนรายละเอียดมีแค่ปุ่มสำเนา/ลบ ไม่มีปุ่มเพิ่ม
DCTK เปิดฟอร์มสินค้าใหม่ได้เฉพาะหลังบันทึกใบกำกับ ซึ่งจะสร้างข้อมูลจริง จึงไม่ทำ)

**ค. ทดลองสลับ 2 ช่องพร้อมกัน**

วิธี differential: วัดผลของช่อง B เดี่ยว ๆ → เทียบกับผลของ B เมื่อตั้ง A ไว้ก่อน
ถ้าต่างกัน = มีกฎที่เกิดจากคู่ (`dist/pairwise-cli.js`)

| หน้า | คู่ที่ทดลอง | ผล |
|---|---|---|
| 1 | 20 คู่ | ต่าง 2 คู่ แต่ **ผลที่เกิดเพิ่ม = ไม่มี** (ช่องเดียวกันถูกเปิดจาก 2 ทาง) |
| 2 | 2 คู่ | **ไม่พบปฏิสัมพันธ์** |
| 3 | 56 คู่ | (ดูผลล่าสุดใน `rules/pairwise.json`) |

> **สรุป: กฎของ DCTK เป็นแบบช่องเดียว ไม่พบกฎที่เกิดจากค่า 2 ช่องรวมกัน**

### กฎกระทบยอดตอนส่งกรมฯ (จากรายงาน `ExDec/ExCheckDiff`)

ปุ่ม **"ตรวจสอบรายละเอียดค่าคำนวนต่าง ๆ"** บนหน้าใบขน เปิดรายงานที่กรมฯ เทียบ
**ส่วนควบคุม (ระดับใบกำกับ)** กับ **ส่วนรายละเอียด (ผลรวมรายการสินค้า)** แล้วแสดง **ผลต่าง**

| กลุ่มที่เทียบ | รายการ |
|---|---|
| เงินต่างประเทศ + เงินบาท | ราคา · ค่าขนส่ง · ค่าระวาง · ค่าประกัน · ค่าบรรจุ · Inland · Landing · อื่นๆ 1 · อื่นๆ 2 |
| น้ำหนักและปริมาณ | น้ำหนักสุทธิ · น้ำหนักรวมหีบห่อ · จำนวนหีบห่อรวม · ปริมาณในใบกำกับ · ปริมาณในใบขน |
| ยอดรวม | ยอด FOB ส่งกรมฯ vs ยอดรวม FOB |

ระบบเราเทียบ **13 รายการ** ครบตามที่กรมฯ เทียบ:

- **เงิน 9 รายการ** — ราคา · ค่าขนส่ง · ค่าระวาง · ค่าประกัน · ค่าบรรจุ · Inland · Landing · อื่นๆ 1 · อื่นๆ 2
- **น้ำหนัก/ปริมาณ 4 รายการ** — น้ำหนักสุทธิ · น้ำหนักรวมหีบห่อ · จำนวนหีบห่อรวม · ปริมาณในใบขน

ถ้าไม่ตรง → เตือนก่อนรัน พร้อมบอกส่วนต่าง (เทียบเฉพาะรายการที่กรอกทั้งสองฝั่ง — ไม่กรอกก็ไม่เตือน)

> 💡 **ไม่ต้องเพิ่มคอลัมน์ใน DB** — ค่าใช้จ่ายต่อรายการที่ไม่มีคอลัมน์เฉพาะ
> (ค่าขนส่ง · ค่าบรรจุ · Inland · Landing · อื่นๆ) เก็บใน `extra_fields` อยู่แล้ว
> ตัวเทียบอ้างด้วย **key ของ registry** จึงอ่านได้ทั้งจากคอลัมน์จริงและจาก `extra_fields`

**ข้อจำกัดที่ยังเหลือ:**
- รายการ "รหัสสถานที่" · "ลำดับอัตราอากร" popup ของ Kendo แสดงทีละไม่กี่รายการ (virtualized)
  กวาดทุกตัวอักษรแล้วยังได้ไม่ครบ — เก็บไว้อ้างอิง ไม่เอาไปตัดสินว่าค่าผิด
- "ปริมาณในใบกำกับ" กรมฯ เทียบด้วย แต่ฝั่งหัวใบของเราไม่มีช่องนี้ (มีแต่ "ปริมาณในใบขน") จึงเทียบได้ 4/5 รายการ

## 2. คลัง Master ข้อมูล

เมนู **"คลัง Master"** — ชุดค่าตั้งต้นที่บันทึกไว้ แยกจากใบขนจริง (ไม่ปนในลิสต์)

### สร้าง Master ได้ 2 ทาง
- **คลัง Master → สร้าง Master ใหม่** — กรอกเองทั้ง 3 หน้า
- **จากใบขนที่ทำสำเร็จแล้ว** → เปิดใบ → ปุ่ม **"บันทึกเป็น Master"** (คัดลอกค่าทั้งใบ + รายการสินค้า)

### โหมดรายช่อง — ตั้งไว้ล่วงหน้าว่าช่องไหนเอาค่าจากไหน

| โหมด | ความหมาย |
|---|---|
| **ใช้ค่า Master** | ใช้ค่าที่กรอกไว้ใน Master เสมอ — **ทับค่าที่ AI สกัดมา** |
| **จาก AI** | ปล่อยให้ AI สกัด — Master เติมให้เฉพาะช่องที่ AI ไม่ได้ค่า |
| **ไม่กรอก** | ข้ามช่องนี้ ไม่กรอกลง DCTK เลย |

ไม่ได้ตั้งเอง = เดาให้อัตโนมัติ — Master มีค่า → *ใช้ค่า Master*, ไม่มีค่า → *จาก AI*

### Master 3 ระดับ (ตามที่ตกลงในที่ประชุม 4 ส.ค. 2569)

AI อ่าน 100% ไม่ได้ จึงต้องมีต้นแบบ 3 ระดับ — ระบบเลือก Master ที่ **ตรงละเอียดที่สุด** ให้อัตโนมัติ

| ระดับ | ช่องใน Master | ความหมาย |
|---|---|---|
| 1. ลูกค้า | `ลูกค้า` | Master นี้ของลูกค้ารายไหน |
| 2. Consignee | `Consignee ที่ใช้ Master นี้` | ใส่ได้**หลายราย** — 3 consignee ใช้ต้นแบบเดียวกันได้ |
| 3. รหัสสินค้า | `รหัสสินค้าที่ใช้ Master นี้` | consignee เดียวกันแต่คนละสินค้า → คนละ Master |

**คะแนนจับคู่:** ตรงรหัสสินค้า ×4 + ตรง consignee ×2 + เป็นค่าเริ่มต้น ×1 + ลำดับความสำคัญ
เว้นว่าง = ใช้ได้ทุกค่า · ระบุไว้แล้วไม่ตรง = ไม่เอา Master นั้น · ไม่ตรงอะไรเลย = ถอยไปใช้ค่าเริ่มต้นของลูกค้า

### ดึงใบเดิมจาก DCTK มาทำ Master อัตโนมัติ

```bash
cd rpa-import-node
set -a; . ../rpa-web/.env; set +a
PULL_INVOICE="DKN 22/2026" PULL_CUSTOMER=THANAKORN node dist/pull-master-cli.js
```

ใส่เลขอะไรก็ได้ — ระบบดูรูปแบบแล้วเลือกคอลัมน์ค้นหาให้เอง
(`DCTK…` = เลขอ้างอิง · `A005-16905-…` = เลขใบขน · ที่เหลือ = **เลขใบกำกับสินค้า**)

อ่านครบทั้ง 3 หน้า + ทุกรายการสินค้า แล้วจับ consignee/รหัสสินค้าให้อัตโนมัติ · `PULL_DRY=1` = ดูอย่างเดียวไม่บันทึก

### เอา Master ไปใช้
- **สร้างใบใหม่จาก Master**: คลัง Master → *สร้างใบ* หรือในฟอร์มสร้างรายการเลือกจากช่อง "เริ่มจาก Master"
  → ฟอร์มเด้งพร้อมค่าครบ แก้ invoice/น้ำหนัก/ราคา แล้วบันทึกได้เลย
  (ค่าที่พิมพ์เองไว้ก่อนกด "ใช้ค่าจาก Master" จะไม่ถูกทับ)
- **อัตโนมัติกับใบที่มาจากอีเมล**: ติ๊ก **"ตั้งเป็นค่าเริ่มต้นของลูกค้านี้ ★"**
  ทุกใบของลูกค้านั้นที่เข้ามาจาก Get Email จะถูกผสมกับ Master ตามโหมดรายช่องข้างต้น
  (1 ลูกค้ามี Master ค่าเริ่มต้นได้ 1 อัน)

โหมดที่ใช้จริงจะถูกบันทึกติดไปกับใบนั้นในคอลัมน์ `declarations.field_modes`
→ worker อ่านตอนกรอก และ **ข้ามช่องที่ตั้งเป็น "ไม่กรอก"** (ชนะทุกกฎ รวมถึง config ลูกค้าเดิม)
